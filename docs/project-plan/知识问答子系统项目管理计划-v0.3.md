## 1. 项目概述

本项目为《软件工程》课程设计“海外藏中国文物知识管理与服务平台”中的知识问答子系统。

知识问答子系统面向平台用户提供海外藏中国文物领域的自然语言问答服务。用户可以围绕文物收藏地、年代、材质、类型、作者、尺寸、相关文物等问题进行提问，系统通过查询 Neo4j 知识图谱和公共 MySQL 数据库，生成自然语言答案，并返回答案来源与原始数据链接。

本组共有 6 名成员。当前阶段主要任务是确定功能范围、技术路线、数据库规划、代码仓库和组内分工，并为后续需求分析、系统设计和开发实现打好基础。

---

## 2. 项目目标

本子系统的总体目标是：

> 基于 Neo4j 知识图谱和公共 MySQL 数据库，实现一个可运行、可集成、可扩展的文物知识问答子系统。

具体目标包括：

1. 支持用户使用自然语言提出文物相关问题。
2. 支持文物收藏地、年代、材质、类型、介绍、作者、尺寸、相关文物等基础问答。
3. 能够通过 Neo4j 查询文物、博物馆、年代、作者之间的关系。
4. 能够通过公共 MySQL 查询文物详情、图片、尺寸、详情页链接等信息。
5. 能够返回自然语言答案，并展示数据来源和原始详情页链接。
6. 对知识库中不存在的问题，明确提示“暂无相关数据”，避免生成不可靠答案。
7. 能够记录问答日志、用户反馈、失败问题和不准确回答审核任务。
8. 能够为 Web 端、App 端和后台管理系统提供接口支持。
9. 第 14 周前完成可独立运行的知识问答子系统 Demo。
10. 第 16 周前配合其他子系统完成集成检查。

## 4. 技术路线概述

本子系统采用：

> 公共 MySQL + Neo4j + FastAPI 问答服务 + Vue 问答页面 的技术路线。

### 4.1 数据源分工

| 数据源 | 作用 |
|---|---|
| 公共 MySQL | 存储文物详情、用户数据、问答日志、用户反馈、失败问题、审核任务和意图模板 |
| Neo4j | 存储文物、博物馆、年代、作者之间的图关系 |
| 大语言模型 / 模板回答 | 用于组织自然语言答案；前期优先使用模板回答，后期视进度接入大模型 |

### 4.2 系统基本流程

```text
用户输入问题
    ↓
FastAPI 问答接口接收问题
    ↓
问题意图识别与实体识别
    ↓
根据 object_id 查询 Neo4j 或公共 MySQL
    ↓
整理查询结果
    ↓
生成自然语言答案
    ↓
返回答案、来源、qaLogId、相关文物等信息
    ↓
记录问答日志、来源记录、失败问题或用户反馈
```

### 4.3 初步技术选型

| 层次 | 技术方案 | 状态 |
|---|---|---|
| 后端 | Python FastAPI | 已确认 |
| 图数据库 | Neo4j | 已确认 |
| 图查询语言 | Cypher | 已确认 |
| 业务数据库 | 公共 MySQL | 已确认 |
| 前端页面 | Vue | 已确认 |
| 接口风格 | RESTful API | 暂定 |
| 代码仓库 | GitHub 独立仓库 | 已建立 |

## 5. 功能规划

根据题目原文要求，本系统功能分为必做功能、选做基础版功能和暂不作为核心的扩展功能。

### 5.1 必做功能

本系统必须完成简单问答与答案溯源功能。

简单问答支持单实体单属性问题，覆盖以下 11 类问题：

| 编号 | 问答类型 | 实现思路 |
|---|---|---|
| 1 | 文物收藏地 | Neo4j 查询文物与博物馆关系，MySQL 补充博物馆信息 |
| 2 | 文物年代 | Neo4j 查询文物与朝代关系，MySQL 补充年代字段 |
| 3 | 文物材质 | MySQL 查询 `artifacts.material`，必要时使用 Neo4j 属性 |
| 4 | 文物类型 | MySQL 查询文物类型字段 |
| 5 | 文物介绍 | MySQL 查询文物简介字段 |
| 6 | 书画作者 | Neo4j 查询文物与作者关系，适用于书画类文物 |
| 7 | 作者生平 | MySQL 查询作者信息，无数据时提示暂无相关数据 |
| 8 | 同一作者作品 | Neo4j 通过作者反查其他文物 |
| 9 | 同一朝代文物 | Neo4j 通过朝代反查相关文物 |
| 10 | 文物尺寸与规格 | MySQL 查询尺寸字段；重量无数据时提示暂无相关数据 |
| 11 | 相关文物推荐 | 按同作者、同朝代、同类型进行基础推荐 |

答案溯源与可信度展示要求每条回答包含：

1. 数据来源说明，例如博物馆名称、公共文物数据库或 Neo4j 知识图谱；
2. 原始文物详情页链接；
3. 对知识图谱 / 数据库事实内容和大语言模型补充性描述进行区分标注。

对于知识图谱或公共数据库中不存在的问题，系统明确提示“暂无相关数据”，不生成不可靠答案。

### 5.2 选做功能基础版

本阶段确定实现以下选做功能的基础版：

| 选做功能 | 本阶段实现范围 |
|---|---|
| 多轮对话 | 支持基于当前 `object_id` 的连续追问，理解“它”“该文物”等简单代词指代，保存最近 5 轮上下文；当用户提出新文物时切换上下文 |
| 复杂问答 | 支持部分统计类和简单多跳关系问答，例如某博物馆收藏数量、某朝代文物数量、收藏某类文物最多的博物馆及所在城市 |
| 问答质量反馈机制 | 每条回答下方提供“有帮助 / 不准确”按钮；不准确回答记录至问题日志或审核任务；统计高频失败或不准确问题类型 |

### 5.3 暂不作为核心功能

以下功能暂不作为第 14 周子系统检查的核心目标：

1. 完整开放式闲聊；
2. 唐宋瓷器风格对比等复杂文化比较问答；
3. 跨多实体路径推理问答；
4. 完整文化导览式长对话。

后续如开发进度允许，可支持限定在文物文化领域内的基础导览问答；对于超出文物文化领域的问题，系统礼貌提示用户本系统主要面向海外藏中国文物知识问答。

### 5.4 第 14 周 MVP 目标

第 14 周前需要完成一个可独立运行的知识问答子系统 Demo，至少包括：

1. 用户可以在页面输入问题；
2. 系统可以回答主要文物基础问题；
3. 系统可以查询 Neo4j 或公共 MySQL 中的数据；
4. 系统可以展示答案来源和详情页链接；
5. 系统可以保存问答日志；
6. 用户可以提交“有帮助 / 不准确”反馈；
7. 系统可以记录无法回答或无数据的问题。

## 6. 数据库规划

### 6.1 复用公共数据库已有表

问答组不重复建设文物、用户、博物馆、作者等基础表，直接复用公共 MySQL 中已有表。

| 表名 | 问答组用途 |
|---|---|
| `artifacts` | 查询文物名称、年代、材质、类型、介绍、尺寸、详情页、图片、`object_id` |
| `museums` | 查询文物收藏博物馆、国家、城市等信息 |
| `dynasties` | 查询朝代信息 |
| `artists` | 查询作者信息和作者生平 |
| `artifact_artist` | 查询文物与作者关系 |
| `artifact_images` | 查询文物图片 |
| `users` | 关联提问用户、反馈用户和审核管理员 |
| `operation_logs` | 管理员操作日志由后台管理组统一负责 |
| `system_logs` | 系统运行日志由后台管理组统一负责 |

### 6.2 问答组新增表

问答组新增表统一放入公共 MySQL 数据库，表名前缀统一为 `qa_`。

| 表名 | 作用 | 优先级 |
|---|---|---|
| `qa_session` | 保存问答会话信息，支持多轮对话上下文 | 推荐实现 |
| `qa_log` | 保存每次用户提问、系统回答、意图类型、回答状态等 | 必须实现 |
| `qa_source_record` | 保存每条回答使用的数据来源、详情页链接和事实内容 | 必须实现 |
| `qa_feedback` | 保存用户“有帮助 / 不准确”反馈 | 必须实现 |
| `qa_review_task` | 保存不准确回答的人工审核任务 | 优先实现 |
| `qa_failed_question` | 保存无法回答、无数据、查询失败等问题 | 必须实现 |
| `qa_intent_template` | 保存意图类型、查询模板和回答模板 | 推荐实现 |

### 6.3 数据库设计原则

1. 不重复建立公共基础表。
2. 问答相关表统一使用 `qa_` 前缀，并放入公共 MySQL 数据库。
3. Web / App 调用问答接口时主要传递 `object_id`。
4. Neo4j `Artifact.object_id` 与 MySQL `artifacts.object_id` 对应。
5. 问答业务表中同时保留 `object_id` 和 `artifact_id`，便于 Neo4j 与 MySQL 双数据源关联。
6. 问答业务数据由问答组维护，后台管理系统原则上通过 API 查询和操作。
7. 管理员审核业务结果记录在 `qa_review_task`，管理员操作日志仍由后台系统记录在公共日志表中。

## 7. 接口规划

当前接口先作为初稿，后续根据 Web、App、后台管理组的需求调整。

| 接口 | 作用 | 使用方 |
|---|---|---|
| `POST /api/qa/ask` | 用户提问，返回答案、来源、`qaLogId` 和相关信息 | Web / App / Vue Demo 页面 |
| `POST /api/qa/feedback` | 提交“有帮助 / 不准确”反馈 | Web / App / Vue Demo 页面 |
| `GET /api/admin/qa/logs` | 查询问答日志 | 后台管理系统 |
| `GET /api/admin/qa/feedback` | 查询用户反馈 | 后台管理系统 |
| `GET /api/admin/qa/failed-questions` | 查询失败问题 | 后台管理系统 |
| `GET /api/admin/qa/review-tasks` | 查询待审核任务 | 后台管理系统 |
| `POST /api/admin/qa/review-tasks/{id}/review` | 提交审核结果 | 后台管理系统 |

说明：虽然所有数据存放在公共数据库中，但问答业务数据仍由问答子系统负责维护。后台管理系统原则上通过问答组提供的接口进行查询和操作；若后期集成时间不足，可允许后台只读查询 `qa_` 表，但审核状态修改、人工修正答案等写操作建议通过 API 完成。

## 11. 当前结论

当前知识问答子系统确定采用 **公共 MySQL + Neo4j + FastAPI + Vue** 的实现路线。

其中：

- 公共 MySQL 负责文物详情、用户数据、问答日志、用户反馈、失败问题、审核任务和意图模板；
- Neo4j 负责文物、博物馆、年代、作者之间的关系查询；
- FastAPI 问答服务负责接收问题、识别意图、查询数据、生成答案并返回来源；
- Vue 问答页面用于 Web 跳转访问和第 14 周子系统运行检查；
- Web 端通过跳转页面集成，App 端通过 API 集成，后台管理系统原则上通过 API 查看和处理问答数据。
