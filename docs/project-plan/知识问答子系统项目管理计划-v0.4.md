# 知识问答子系统项目管理计划 v0.4

## 1. 版本说明

本版本基于 v0.3 项目管理计划、课设题目原文、组内分工说明以及当前主分支实现情况进行更新。

v0.4 的核心调整是：将原先“公共 MySQL + Neo4j + FastAPI + Vue”的问答系统规划，升级为更符合课设题目要求的：

```text
公共 MySQL + Neo4j 知识图谱 + FastAPI + Vue + 可配置大语言模型的轻量 RAG 问答架构
```

本版本同时记录当前主分支已经完成的工程化改进，以及第 14 周子系统检查前需要继续补强的功能点。

---

## 2. 项目概述

本项目为《软件工程》课程设计“海外藏中国文物知识管理与服务平台”中的知识问答子系统。

知识问答子系统面向平台用户提供海外藏中国文物领域的自然语言问答服务。用户可以围绕文物收藏地、年代、材质、类型、介绍、作者、尺寸、相关文物等内容进行提问。系统通过 MySQL 公共数据库和 Neo4j 知识图谱检索事实依据，并在可配置大语言模型的支持下生成自然语言回答，同时返回答案来源、事实内容、补充描述和原始详情页链接。

本系统不允许在无事实依据的情况下编造答案。对于 MySQL 或 Neo4j 中暂无数据的问题，系统应明确提示“暂无相关数据”，并记录失败问题，供后续数据补充和人工审核。

---

## 3. 项目目标

本子系统总体目标是：

> 基于公共 MySQL、Neo4j 知识图谱和轻量 RAG 生成流程，实现一个可运行、可集成、可溯源、可扩展的海外藏中国文物知识问答子系统。

具体目标包括：

1. 支持用户使用自然语言提出文物相关问题。
2. 支持文物收藏地、年代、材质、类型、介绍、书画作者、作者生平、同作者作品、同朝代文物、尺寸规格和相关文物推荐等基础问答。
3. 支持 Neo4j 查询文物、博物馆、朝代、作者等实体之间的图关系。
4. 支持公共 MySQL 查询文物详情、图片、尺寸、原始详情页链接等结构化信息。
5. 支持轻量 RAG 流程：先检索 MySQL / Neo4j 事实，再将事实作为上下文交给大语言模型生成补充性自然语言回答。
6. 支持未配置大语言模型时自动回退到模板生成，保证系统可独立运行。
7. 明确区分 `factContent` 和 `supplementalContent`：事实内容来自 MySQL / Neo4j，补充描述来自模板或大语言模型。
8. 返回数据来源、来源类型、原始详情页链接和可信度标记。
9. 对知识库中不存在的问题明确返回“暂无相关数据”，避免生成不可靠答案。
10. 记录问答日志、答案来源、用户反馈、失败问题和不准确回答审核任务。
11. 为 Web 端、App 端和后台管理系统提供统一接口。
12. 第 14 周前完成可独立运行、可演示、可测试的知识问答子系统 Demo。
13. 第 16 周前配合其他子系统完成整体集成检查。

## 4. 技术路线

### 4.1 总体架构

本系统采用如下技术路线：

```text
Vue 问答页面 / Web / App
        ↓
FastAPI 问答后端 /api/qa/ask
        ↓
意图识别 + 实体抽取 + objectId 解析 + 多轮上下文
        ↓
MySQL 文物详情查询 + Neo4j 图谱关系查询
        ↓
轻量 RAG 生成层
        ↓
答案、事实内容、补充描述、来源、推荐文物、反馈入口
        ↓
问答日志、来源记录、失败问题、用户反馈、审核任务
```

### 4.2 数据源与生成层分工

| 模块 | 作用 |
|---|---|
| 公共 MySQL | 存储文物详情、原始详情页链接、图片、用户数据、问答日志、用户反馈、失败问题、审核任务和意图模板 |
| Neo4j | 存储文物、博物馆、朝代、作者之间的图关系，支持关系问答、推荐、统计和多跳查询 |
| 大语言模型 | 在已有事实基础上生成补充性自然语言描述，不作为事实来源，不允许编造事实 |
| 模板回答 | 当 LLM 未配置、调用失败或无需补充说明时，作为稳定兜底生成方式 |

### 4.3 轻量 RAG 约束

本系统的 RAG 采用“结构化事实检索 + 受约束生成”的轻量实现方式，不在第 14 周前强制引入向量数据库。

轻量 RAG 流程如下：

```text
1. 根据问题识别意图和实体。
2. 查询 MySQL / Neo4j，得到事实列表 facts 和来源 sources。
3. 将用户问题、意图、文物对象、facts、sources 组织成 prompt。
4. 调用大语言模型生成 supplementalContent。
5. 模型只能基于 facts 改写和补充表达，不允许新增未检索到的事实。
6. 如果 facts 为空，则不调用模型生成事实性答案，直接返回“暂无相关数据”。
7. 如果 LLM 未配置或调用失败，则返回模板答案，并记录回退原因。
```

前端展示时必须区分：

| 字段 | 含义 |
|---|---|
| `factContent` | MySQL / Neo4j 检索得到的事实内容 |
| `supplementalContent` | 模板或大语言模型生成的补充性描述 |
| `sources` | 所有事实来源和模型补充来源 |

## 5. 功能范围

### 5.1 必做功能

本系统必须完成简单问答、答案溯源和可信度展示。

简单问答覆盖以下 11 类：

| 编号 | 问答类型 | 实现思路 |
|---|---|---|
| 1 | 文物收藏地 | Neo4j 查询收藏关系，必要时 MySQL 补充博物馆信息和详情链接 |
| 2 | 文物年代 | Neo4j 查询朝代关系，MySQL 补充 `time_period` 或朝代字段 |
| 3 | 文物材质 | MySQL 查询 `artifacts.material` |
| 4 | 文物类型 | MySQL 查询 `artifacts.type` |
| 5 | 文物介绍 | MySQL 查询 `artifacts.description` |
| 6 | 书画作者 | Neo4j 查询 `CREATED_BY` 关系，MySQL 补充作者信息 |
| 7 | 作者生平 | MySQL 查询作者表中的 biography 字段 |
| 8 | 同一作者作品 | Neo4j 通过作者节点反查其他文物 |
| 9 | 同一朝代文物 | Neo4j 通过朝代节点反查相关文物；支持从当前文物或朝代实体出发 |
| 10 | 文物尺寸与规格 | MySQL 查询 `artifacts.dimensions`，无重量数据时明确提示暂无 |
| 11 | 相关文物推荐 | 综合同作者、同朝代、同类型规则进行基础推荐 |

答案溯源要求每条可回答结果尽量包含：

1. 数据来源说明；
2. 原始文物详情页链接；
3. 知识图谱 / 数据库事实内容；
4. 模板或大语言模型补充描述；
5. 数据来源类型，例如 `mysql`、`neo4j`、`llm`、`template`。

### 5.2 选做功能基础版

| 选做功能 | 第 14 周实现范围 |
|---|---|
| 多轮对话 | 支持基于当前 `objectId` 的连续追问，保存最近 5 轮上下文，理解“它”“该文物”等代词；当前采用内存上下文，后续可持久化到 `qa_session` |
| 复杂问答 | 支持博物馆文物数量统计、收藏某类型最多的博物馆、博物馆所在城市、某朝代代表性文物等基础复杂问答 |
| 问答质量反馈机制 | 支持“有帮助 / 不准确”反馈；不准确反馈生成审核任务；后台可统计高频失败和高频不准确问题类型 |
| 轻量 RAG 生成 | 在有事实检索结果时调用可配置大语言模型生成补充说明；未配置时自动模板回退 |

### 5.3 暂不作为第 14 周核心目标

以下内容暂不作为第 14 周子系统检查的核心目标：

1. 完整开放式闲聊；
2. 大规模向量检索和全文语义检索；
3. 唐宋瓷器风格对比等复杂文化比较问答；
4. 跨多个实体路径的复杂推理问答；
5. 完整文化导览式长对话；
6. 多轮上下文的长期持久化和跨设备同步。

## 6. 当前主分支已完成和已明确的工程化改进

### 6.1 objectId 优先级调整

当前主分支采用如下 `objectId` 解析优先级：

```text
1. 问题中明确识别出的唯一文物名称；
2. 请求体或 URL 传入的 objectId；
3. sessionId / conversationId 对应的会话上下文；
4. 多候选文物时返回候选列表；
5. 无法确定时提示用户补充文物名称或从详情页进入。
```

该优先级相比最初分工说明有工程化调整：请求传入的 `objectId` 优先于旧会话上下文。原因是 Web / App 从文物详情页跳转到问答页时，URL 或请求体中的 `objectId` 代表用户当前正在查看的文物，比历史会话上下文更可靠。

### 6.2 IntentResult.entities 扩展

为支持不依赖单个文物对象的复杂问答，当前主分支已经扩展：

```text
IntentResult.entities: dict[str, Any]
```

典型实体包括：

| 键名 | 用途 |
|---|---|
| `museum` | 统计某博物馆收藏数量、查询博物馆城市 |
| `artifact_type` | 查询收藏某类型文物最多的博物馆 |
| `dynasty` | 查询某朝代代表性文物 |

### 6.3 后台统计接口升级

“高频失败问题类型”和“高频不准确问题类型”已经从文档统计要求升级为可调用 API：

```text
GET /api/admin/qa/statistics/failure-types
GET /api/admin/qa/statistics/inaccurate-types
```

测试报告和阶段分析文档应基于这些接口进行说明。

### 6.4 测试方式升级

当前项目不仅包含测试用例文档，还包含可执行的 pytest 自动化测试。后端修改后应至少执行：

```powershell
cd backend
python -m pytest tests
```

前端修改后应至少执行：

```powershell
cd frontend
npm run build
```

### 6.5 前端独立演示能力

Vue 问答页面已经支持：

1. URL 接收 `objectId`；
2. 子系统独立演示时手动输入或选择演示文物；
3. 问答对话展示；
4. `factContent` 和 `supplementalContent` 分区展示；
5. 来源展示和详情页链接展示；
6. 相关文物推荐展示；
7. “有帮助 / 不准确”反馈提交。

### 6.6 真实数据源连接

当前主分支已经支持连接公共 MySQL 和 Neo4j，并能完成部分真实查询。由于当前数据库和图谱样例数据较少，第 14 周演示时应准备固定样例问题，避免使用无数据样例影响演示效果。

## 8. 数据库规划

### 8.1 复用公共数据库已有表

问答组不重复建设文物、用户、博物馆、作者等基础表，直接复用公共 MySQL 中已有表。

| 表名 | 问答组用途 |
|---|---|
| `artifacts` | 查询文物名称、年代、材质、类型、介绍、尺寸、详情页、图片、`object_id` |
| `museums` | 查询文物收藏博物馆、国家、城市等信息 |
| `dynasties` | 查询朝代信息 |
| `artists` | 查询作者信息和作者生平 |
| `artifact_artist` | 查询文物与作者关系 |
| `artifact_images` | 查询文物图片 |
| `users` | 关联提问用户、反馈用户和审核管理员 |
| `operation_logs` | 管理员操作日志由后台管理组统一负责 |
| `system_logs` | 系统运行日志由后台管理组统一负责 |

### 8.2 问答组新增表

问答组新增表统一放入公共 MySQL 数据库，表名前缀统一为 `qa_`。

| 表名 | 作用 | 优先级 |
|---|---|---|
| `qa_session` | 保存问答会话信息，支持多轮对话上下文 | 推荐实现 |
| `qa_log` | 保存每次用户提问、系统回答、意图类型、回答状态等 | 必须实现 |
| `qa_source_record` | 保存每条回答使用的数据来源、详情页链接和事实内容 | 必须实现 |
| `qa_feedback` | 保存用户“有帮助 / 不准确”反馈 | 必须实现 |
| `qa_review_task` | 保存不准确回答的人工审核任务 | 优先实现 |
| `qa_failed_question` | 保存无法回答、无数据、查询失败等问题 | 必须实现 |
| `qa_intent_template` | 保存意图类型、查询模板和回答模板 | 推荐实现 |

### 8.3 数据库设计原则

1. 不重复建立公共基础表。
2. 问答相关表统一使用 `qa_` 前缀，并放入公共 MySQL 数据库。
3. Web / App 调用问答接口时主要传递 `objectId`。
4. Neo4j `Artifact.object_id` 与 MySQL `artifacts.object_id` 对应。
5. 问答业务表中同时保留 `object_id` 和 `artifact_id`，便于 Neo4j 与 MySQL 双数据源关联。
6. 问答业务数据由问答组维护，后台管理系统原则上通过 API 查询和操作。
7. 大语言模型生成内容不写入事实字段，应单独记录在 `supplemental_content` 或来源类型为 `llm` 的记录中。

## 9. 接口规划

### 9.1 用户侧接口

| 接口 | 作用 | 使用方 |
|---|---|---|
| `POST /api/qa/ask` | 用户提问，返回答案、来源、`qaLogId`、事实内容、补充描述和相关文物 | Web / App / Vue Demo 页面 |

### 9.2 后台管理接口

| 接口 | 作用 | 使用方 |
|---|---|---|
| `GET /api/admin/qa/logs` | 查询问答日志 | 后台管理系统 |
| `GET /api/admin/qa/feedback` | 查询用户反馈 | 后台管理系统 |
| `GET /api/admin/qa/failed-questions` | 查询失败问题 | 后台管理系统 |
| `GET /api/admin/qa/review-tasks` | 查询待审核任务 | 后台管理系统 |
| `POST /api/admin/qa/review-tasks/{id}/review` | 提交审核结果 | 后台管理系统 |
| `GET /api/admin/qa/statistics/failure-types` | 统计高频失败问题类型 | 后台管理系统 / 测试报告 |
| `GET /api/admin/qa/statistics/inaccurate-types` | 统计高频不准确问题类型 | 后台管理系统 / 测试报告 |

### 9.3 ask 响应关键字段

| 字段 | 说明 |
|---|---|
| `answer` | 用户可直接阅读的回答，优先基于事实和模板生成 |
| `factContent` | MySQL / Neo4j 检索得到的事实内容 |
| `supplementalContent` | 模板或大语言模型生成的补充描述 |
| `sources` | 来源列表，包含 `mysql`、`neo4j`、`llm`、`template` |
| `relatedArtifacts` | 相关文物推荐结果 |
| `qaLogId` | 反馈接口使用的问答日志标识 |

## 12. 质量要求

1. 所有事实性回答必须来自 MySQL 或 Neo4j。
2. 大语言模型只能基于检索事实生成补充描述，不允许编造未检索到的事实。
3. 知识库无数据时必须返回“暂无相关数据”或具体无数据提示。
4. 前端必须区分展示事实内容和补充描述。
5. 每条可回答结果应尽量返回来源和原始详情页链接。
6. 用户反馈为“不准确”时必须生成审核任务。
7. 后端修改后必须运行自动化测试。
8. 前端修改后必须运行构建检查。
9. `main` 分支应保持可运行，队友通过 PR 合并，组长负责审核接口契约和集成风险。
10. 数据库、Neo4j、LLM 等敏感连接信息不得提交到 GitHub 仓库。

## 13. 当前结论

当前知识问答子系统已经完成 FastAPI 后端、Vue 前端、MySQL 接入、Neo4j 接入、问答主流程、反馈审核、后台接口和自动化测试的基础集成。

v0.4 阶段的核心任务是把系统从“数据库 / 图谱检索 + 模板回答”的基础问答 Demo，升级为更符合课设题目要求的“知识图谱 + 大语言模型”的轻量 RAG 问答系统。

升级后的系统应具备以下特点：

```text
事实来自 MySQL / Neo4j
表达可由 LLM 辅助生成
无事实不编造
事实内容和补充描述分开展示
来源可追溯
未配置 LLM 时仍可模板回退运行
```

在此基础上，第 14 周子系统检查可以重点展示：

1. 文物基础问答；
2. 图谱关系问答；
3. 统计类复杂问答；
4. 多轮上下文追问；
5. RAG 补充生成；
6. 答案来源和详情页链接；
7. 反馈与审核任务；
8. 后台统计接口；
9. 自动化测试和演示脚本。
