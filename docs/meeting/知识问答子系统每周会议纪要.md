## 第 8 周会议纪要：项目启动与任务分工

会议主题：确定知识问答子系统目标、技术路线和组内分工。

主要讨论内容：

1. 明确知识问答子系统在整体平台中的定位：面向海外藏中国文物数据，提供自然语言问答服务。
2. 确定系统核心流程：

```text
用户输入问题
→ 后端接收问题
→ 识别问题类型和文物对象
→ 查询 MySQL 或 Neo4j
→ 生成回答并标注来源
→ 前端展示答案、来源和推荐文物
→ 用户反馈
→ 系统记录日志、反馈和审核任务
```

3. 初步确定使用 FastAPI 作为后端框架，Vue 作为前端页面，MySQL 存储结构化数据和问答业务数据，Neo4j 支撑图谱关系查询。
4. 明确本组采用模块负责制，共 6 名成员分别负责后端主流程、MySQL 数据访问、Neo4j 图谱查询、意图识别与答案生成、前端页面、反馈审核与测试文档。

形成决议：

1. 以 `objectId` 作为知识问答子系统统一文物标识。
2. 由组长负责项目计划、接口规范、后端主流程、代码集成和最终联调。
3. 各成员并行开发，后续通过统一 API、统一数据模型和 GitHub PR 进行集成。

会后任务：

| 负责人 | 任务 |
|---|---|
| 组长 | 编写项目管理计划，规划后端主流程和接口结构 |
| 成员 2 | 梳理 MySQL 业务表和公共文物表访问需求 |
| 成员 3 | 梳理 Neo4j 查询场景和复杂问答需求 |
| 成员 4 | 梳理 11 类简单问答意图与常见问法 |
| 成员 5 | 准备 Vue 问答页面设计 |
| 成员 6 | 准备反馈、审核、测试和文档目录 |

## 第 9 周会议纪要：需求分析与问答范围确认

会议主题：确认知识问答子系统功能需求和第 14 周阶段目标。

主要讨论内容：

1. 对照课程设计题目，确认必做功能包括简单问答、暂无数据提示、答案来源说明、原始详情页链接、事实内容与补充说明区分。
2. 确认简单问答覆盖范围，包括：

```text
文物收藏地
文物年代
文物材质
文物类型
文物介绍
书画作者
作者生平
同一作者作品
同一朝代文物
文物尺寸与规格
相关文物推荐
```

3. 确认选做功能基础版包括多轮对话、复杂问答基础版和问答质量反馈机制。
4. 明确系统遇到知识库无数据时必须返回“暂无相关数据”或提示补充文物名称，不允许生成不可靠答案。

形成决议：

1. 第 14 周前目标为完成可独立运行、可演示、可测试的知识问答子系统 Demo。
2. 复杂问答第 14 周先实现基础版，重点覆盖统计类、多跳类、同朝代文物和相关文物推荐。
3. 闲聊与文化导览暂不作为第 14 周核心目标，系统优先保证文物知识问答的准确性和可信度。

会后任务：

| 负责人 | 任务 |
|---|---|
| 组长 | 更新项目管理计划，明确 MVP 范围 |
| 成员 2 | 继续完善问答业务表设计 |
| 成员 3 | 准备图谱查询模板 |
| 成员 4 | 准备意图编码和兜底话术 |
| 成员 5 | 确认前端展示字段 |
| 成员 6 | 梳理测试用例和反馈审核需求 |

## 第 10 周会议纪要：系统设计与接口规范

会议主题：确定后端架构、接口契约、数据流和模块边界。

主要讨论内容：

1. 确认后端采用分层结构，包括 API 层、Schema 层、Service 层、Repository 层和 Models 层。
2. 确认主接口为：

```text
POST /api/qa/ask
```

3. 确认反馈接口为：

```text
POST /api/qa/feedback
```

4. 设计统一响应字段，包括 `qaLogId`、`sessionId`、`status`、`intent`、`answer`、`factContent`、`supplementalContent`、`resolvedObject`、`sources`、`relatedArtifacts`、`debug` 等。
5. 讨论 `objectId` 解析规则，并确认需要同时支持 URL / 请求参数传入、问题中识别文物名称和会话上下文。

形成决议：

1. 所有队友模块接入时必须遵守统一请求和响应格式。
2. `objectId` 作为 Web、App、MySQL、Neo4j、问答日志和反馈记录之间的统一关联字段。
3. 当前工程优先保证接口稳定，后续字段变更必须同步更新 API 文档和接入说明。

会后任务：

| 负责人 | 任务 |
|---|---|
| 组长 | 搭建 FastAPI 基础框架，编写 API 文档初稿 |
| 成员 2 | 输出数据库设计文档和建表 SQL |
| 成员 3 | 输出 Neo4j schema 分析和 Cypher 模板 |
| 成员 4 | 输出意图识别与上下文设计文档 |
| 成员 5 | 根据 API 响应字段设计前端组件 |
| 成员 6 | 设计后台管理接口初稿 |

## 第 12 周会议纪要：数据库与知识图谱接入

会议主题：接入公共 MySQL 和 Neo4j，推进真实数据查询。

主要讨论内容：

1. 成员 2 提交 MySQL 数据库设计，组内围绕 `qa_session`、`qa_log`、`qa_source_record`、`qa_feedback`、`qa_review_task`、`qa_failed_question`、`qa_intent_template` 等表进行审核。
2. 成员 3 提交 Neo4j 图谱查询模块，讨论统计类问答是否只能依赖 `objectId`。
3. 组内确认复杂问答中可以引入 `entities` 字段，用于承载博物馆名、朝代名、类型名等实体，避免所有统计查询都必须从单件文物出发。
4. 讨论 MySQL、Neo4j 和问答日志中的 `objectId` 一致性问题。

形成决议：

1. 成员 3 的统计类、朝代类、类型类复杂问答允许通过实体字段查询，不强制要求所有问题都先解析到某件文物。
2. 成员 2 的数据库设计需要支撑问答日志、来源记录、失败问题和反馈审核。
3. 图谱查询和 MySQL 查询都必须通过统一服务接入 `/api/qa/ask` 主流程。

会后任务：

| 负责人 | 任务 |
|---|---|
| 组长 | 审核数据库设计和 Neo4j PR，必要时进行集成修复 |
| 成员 2 | 根据审核意见完善数据库设计与查询代码 |
| 成员 3 | 补充实体查询、复杂问答和图谱查询说明 |

## 第 16 周会议纪要：跨子系统集成对接

会议主题：与 Web、App、知识图谱和后台管理子系统进行集成准备。

主要讨论内容：

1. 梳理知识问答子系统需要对接的其他子系统：

```text
知识图谱构建子系统
掌上博物馆 App
后台管理子系统
```

2. 与 App 子系统明确对接方式：App 端直接调用知识问答后端接口，传入 `question`、`objectId`、`sessionId`、`sourceClient=app` 等字段。
3. 与后台管理子系统明确对接方式：后台优先调用 `/api/admin/qa/*` 接口查看问答日志、用户反馈、失败问题、审核任务和统计结果，不建议直接定时扫描数据库表。
4. 明确本阶段如果暂时不部署到统一服务器，可以使用组长本机作为临时后端服务，对接组通过局域网地址访问接口。
5. 讨论正式部署要求：需要 Python、Node.js、Git、端口开放、数据库和 Neo4j 连接，以及可访问 LLM API 的网络环境。

形成决议：

1. 向 App 组提供 `docs/integration/app-integration-guide.md`。
2. 向后台管理组提供 `docs/integration/admin-integration-guide.md`。
3. 本机临时联调地址以实际 `ipconfig` 获取的 WLAN IPv4 为准，后端启动时使用：

```text
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

4. 后续正式集成时，若改为服务器部署或统一网关转发，需要同步更新 baseURL 和 CORS 配置。

## 阶段总结

截至第 16 周，知识问答子系统已完成第 14 周子系统检查所需的核心功能，并进入跨子系统集成阶段。系统已经具备以下能力：

1. 支持 11 类文物简单问答；
2. 支持 MySQL 结构化数据查询；
3. 支持 Neo4j 图谱关系查询；
4. 支持轻量 RAG 补充说明；
5. 支持答案来源、详情页链接和事实/补充分区展示；
6. 支持多轮上下文基础版；
7. 支持复杂问答基础版；
8. 支持用户反馈、不准确回答审核和后台统计；
9. 支持前端独立演示；
10. 支持 App 和后台管理子系统接口对接。

后续重点工作：

1. 配合其他子系统完成最终联调；
2. 根据统一部署方案调整 baseURL、CORS 和运行方式；
3. 如时间允许，完善 `qa_session` 持久化、多轮历史记录和更复杂的推理问答；
4. 根据后台管理和 App 组反馈，补充必要接口字段或展示说明。
